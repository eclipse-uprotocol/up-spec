== Overview

This document is the single source of truth for uProtocol payload-encoding
identity. A UMessage carries the identity of its payload's encoding as the
`payloadEncodingId` attribute defined in
xref:uattributes.adoc[uProtocol Attributes (UAttributes)]. That attribute holds
a 16-bit identifier; this registry defines what the identifiers mean, how the
identifier space is partitioned, and how new identifiers are assigned.
This document is authoritative for registry assignments; contract-defined and
private-use meanings come from their applicable contracts.

The registry answers one question: _how are these payload bytes encoded?_ It
deliberately does not answer three neighbouring questions, which are governed
elsewhere:

* whether a particular producer is permitted to put a given identifier on the
  wire (xref:#allocation[allocation and origination]);
* whether a particular component supports decoding a given encoding
  (xref:#acceptance[carrying a payload versus reading it]); and
* which concrete message type, schema, or memory layout a payload conforms to
  (xref:#type-identity[encoding identity versus type identity]).

Keeping these separate lets intermediaries preserve identifiers they do not
understand, lets deployments extend the space privately, and lets decoders
reject what they cannot process without making the protocol reject what it can
carry.

[#obligations]
=== Requirement Ownership

Obligations on applications and deployments are _assumptions of use_, identified
by specification items with an `aou~` prefix and expressed with *SHALL* or
*SHALL NOT*. Requirements on uProtocol components remain in their respective
specifications, using *MUST* or *MUST NOT*. Registry-governance requirements apply
to the maintainers of this registry.

*MUST* and *SHALL* both retain their BCP14 meaning of an absolute requirement.
The convention distinguishes the responsible party, not the obligation's strength.
For example, application-level preservation is an assumption of use here, while
the Transport Layer's xref:../up-l1/README.adoc#send[Send() contract]
defines preservation requirements for transport implementations.

[#partition]
== Identifier Space

The identifier space is the closed range `0x0000` to `0xFFFF`. It is
partitioned as follows:

[cols="2,2,6", options="header"]
|===
|Range |Name |Meaning

|`0x0000`
|Contract-defined
|The concrete encoding is defined by an applicable transport binding, service
contract, or schema contract rather than by this registry. The identifier is
present; its meaning is delegated.

|`0x0001` to `0xDFFF`
|Registry assignments
|Identifiers assigned by this registry. Unassigned identifiers in this range
are structurally valid; producer restrictions are defined in
xref:#allocation[Allocation and Origination].

|`0xE000` to `0xEFFF`
|Reserved
|Not available for assignment or private use. Reserved identifiers are
structurally valid so that they can be preserved by intermediaries; producer
restrictions are defined in xref:#allocation[Allocation and Origination].

|`0xF000` to `0xFFFE`
|Private use
|Never assigned by this registry. Valid on the wire and carry meaning only by
deployment-level agreement.

|`0xFFFF`
|Reserved
|Reserved for possible future matching on payload-encoding identity. Not
available for assignment or private use. Structurally valid for preservation;
producer restrictions are defined in xref:#allocation[Allocation and Origination].
|===

This revision defines no wildcard matching behavior. A carrying component
preserves `0xFFFF` as an opaque reserved identifier, not a match-all value.
Moving an existing private use of `0xFFFF` to another agreed identifier is a
deployment-level migration, not a relabeling performed by intermediaries.

This is an independent uProtocol registry. Its identifiers do not reuse the
numeric values of the IANA CoAP Content-Formats registry, and identifiers
`0x0001` to `0x0007` preserve the numeric values of the `UPayloadFormat`
enumeration that this registry replaces.

=== Private-use Identifiers

Private use is a normative part of the identifier model. Identifiers in
`0xF000` to `0xFFFE` are valid on the wire, are never assigned by this registry,
and have meanings defined by deployment-level agreement. The assumptions of use in
xref:#allocation[Allocation and Origination] and
xref:#acceptance[Carrying a Payload versus Reading It] govern their origination,
preservation and interpretation.

==== Example of Private Allocation Coordination (Non-normative)

These rules support long-lived proprietary encodings as well as encodings
awaiting a public registry assignment. An allocation plan can reserve separate
blocks for shared library conventions, generated native-representation tables,
and non-public formats managed by different organizations, vendors or products.
For example, parties sharing an interpretation agreement could coordinate the
following allocation:

[cols="2,6", options="header"]
|===
|Example private block |Allocation owner or use

|`0xF000` to `0xF0FF`
|Shared library-profile conventions, including encodings awaiting registration.

|`0xF100` to `0xF7FF`
|Deployment-managed native representation tables.

|`0xF800` to `0xFBFF`
|Non-public formats managed by one organization or vendor.

|`0xFC00` to `0xFFFE`
|Non-public formats managed by another organization or vendor.
|===

The number, sizes and ownership of these blocks are choices made by the parties
to the agreement. They can allocate additional or differently sized blocks as
their production formats require. Such private reservations are distinct from
the registry's Reserved category and are not public registry assignments.
This example adds no restriction on carriage. A library's built-in private value
has meaning only through the applicable agreement. A deployment with a
conflicting allocation can select its own codec identity and coordinate that
meaning with its interpreting peers.

If an encoding later receives a public registry assignment, implementations and
deployments coordinate migration to the assigned identifier. An earlier private
value retains only its agreed private meaning; it does not automatically become
an alias of the registered identifier. Proprietary encodings can continue using
an agreed private allocation without seeking public registration.

This partition applies to payload-encoding identifiers only. Selected-wire,
payload-family, and metadata-layout identities are outside the scope of this
registry.

[#acceptance]
== Carrying a Payload versus Reading It

[.specitem,oft-sid="aou~payload-encoding-opaque-carriage~1",oft-title="Opaque payload carriage"]
--
A component that only carries, routes, stores, or forwards a message *SHALL*
preserve its identifier and payload bytes unchanged. It *SHALL NOT* require a
decoder or reject carriage because the identifier is reserved, unassigned,
private, or unknown to it. Recognizing an identifier does not require reading
the payload; learning an identifier's meaning later *SHALL NOT* invalidate
previously acceptable carriage.
--

The message-validation rules are defined once,
on `payloadEncodingId` in xref:uattributes.adoc[UAttributes].

[.specitem,oft-sid="aou~payload-encoding-supported-decoding~1",oft-title="Supported payload decoding"]
--
A component that reads a payload *SHALL* first determine its encoding. It *SHALL*
reject the payload if it cannot determine or does not support that encoding.
--

This is a decoding decision, not a restriction on which valid identifiers a
message can carry.

[#allocation]
== Allocation and Origination

This section says who may put which identifiers on the wire. These are
obligations on producers and deployments, not checks a receiver performs.
A component that forwards a message it did not create is not its producer.

[.specitem,oft-sid="aou~payload-encoding-origination~1",oft-title="Payload identifier origination"]
--
* A producer *SHALL NOT* originate an identifier in the registry-assignment
  range that this registry has not assigned.
* A producer *SHALL NOT* originate any reserved identifier.
--

[.specitem,oft-sid="aou~payload-encoding-private-agreement~1",oft-title="Private payload encoding agreement"]
--
A producer *MAY* originate a private-use identifier. When doing so, it *SHALL*
use a deployment agreement that defines its meaning for every party that will
interpret it.
--

[.specitem,oft-sid="aou~payload-encoding-contract-defined~1",oft-title="Contract-defined payload encoding"]
--
A producer *MAY* originate `0x0000` only where an applicable binding,
service contract, or schema contract defines the concrete encoding for every
party that will interpret the payload. A component that interprets such a
payload *SHALL* have that contract and *SHALL NOT* infer the encoding from the
payload data.
--

A library *MAY* refuse to construct a message that would originate a reserved
identifier. This is a producer-side convenience, not message validation: a
received or forwarded message carrying a reserved identifier is still preserved
unchanged.

Forwarding, relaying, storing, or re-encoding the envelope of an existing
message is not origination: a component that carries a message it did not
create does not originate its identifier and is not subject to the origination
rules above, only to the preservation rules in
xref:#acceptance[Carrying a Payload versus Reading It].

=== Registry Governance

A registry assignment is permanent and *MUST NOT* be reassigned or withdrawn.
New assignments are made by changing the table in xref:#assignments[Registry
Assignments] through the normal up-spec review process; changing the
identifier-space partition is not required for a new assignment.

Each assignment *MUST* provide:

* a stable name;
* a precise description of the encoding;
* a representation category, `Text` or `Binary`, describing whether the
  encoded octets are a UTF-8 character sequence or arbitrary octets;
* a normative reference to a formal, publicly available specification of the
  encoding; and
* a registered media type when one accurately identifies the encoding, or
  `None registered` otherwise.

The representation category and media type are semantic descriptions of the
encoding. They support explicit, application-aware operations such as
projecting a payload into another format's native data model.

[.specitem,oft-sid="aou~payload-encoding-category-independent-carriage~1",oft-title="Category-independent payload carriage"]
--
Representation category and media type are not carriage admission criteria.
A carrying component *SHALL NOT* change how it
carries a payload because it recognizes the identifier's category.
--

[#type-identity]
== Encoding Identity versus Type Identity

The identifier says how a payload is encoded, not which type, schema, or memory
layout it uses. Protobuf (`2`) still needs a message type, and SOME/IP (`4`, `5`)
still needs a service-interface definition. Contract-defined (`0`) delegates the
encoding itself to an applicable contract. A reader gets the required type,
schema, or layout from that contract, a schema reference such as CloudEvents
`dataschema`, or a binding/profile mechanism. The identifier alone establishes
neither application-schema compatibility nor native ABI compatibility.
This registry defines no mechanism for conveying a separate type or layout
identity; the applicable contract or profile defines how to carry and preserve it.
